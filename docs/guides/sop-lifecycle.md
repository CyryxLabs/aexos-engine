# SOP lifecycle contracts

AEXOS SOP v1 keeps a canonical JSON contract and produces deterministic Markdown for readers. The contract owns step, branch, exception, approval, and evidence identities. Markdown is a projection and is never lifecycle authority.

Use the standalone commands to validate a contract, render its projection, detect projection drift, preview workflow-map compilation and inspect protected history. All compilation is structural and non-executable: no SOP execution adapter is registered. Existing mapper classifications and conditional, exception, manual, external, agentic and approval requirements remain visible.

Trusted lifecycle changes use the in-process SOP authority seam. A trusted host binds its dispatch identity to an exact live CapabilityBroker lease. The lease binds the SOP ID, version, semantic hash, transition intent, action, and project. Review resolution is checked between two live lease verifications. Role strings, imported booleans, compiler PASS, serialized leases, and caller-supplied brokers are declarations rather than authority.

The standalone CLI deliberately denies lifecycle transition with `SOP_AUTHORITY_UNAVAILABLE`. Production identity enrollment, independent review receipt resolution, and runtime receipt association remain host integration requirements. Fixture hosts keep `fixture` assurance, and fixture evidence yields `fixture-conformance` at most.

Lifecycle history belongs in an existing absolute operator control directory outside the consumer project. Versions are immutable; later semantic content uses a new Draft version with a reason, compatibility impact, affected consumers, and supersession link. Replacing an Effective version records the old Superseded and new Effective views in one append-only event.

Every canonical version change requires semantic review. `render-only` is rejected on canonical contracts, including Draft versions; presentation changes belong to regenerated human projections and cannot create a new canonical version.

Canonical JSON must declare `lifecycleState: Draft`; approval is never imported from content. Lifecycle replay produces a deeply frozen, privately branded snapshot with state in `snapshot.lifecycle.state`. Only that exact live object can authorize approved compilation or conformance. Serialized copies and stale snapshots fail closed. Replay checks every legal transition, complete content/semantic/version identity, project and host/canonical policy identity, monotonic nonfuture timestamps, retained creator and enrolled owner, exact review receipts and fresh independent gates. The stricter host/contract review-age limit wins. Old records lacking this evidence are not silently upgraded.

Host construction is a trusted JavaScript composition boundary, not an identity-enrollment API. The application must own a real CapabilityBroker, immutable policy identity, dispatch identity resolver, independent receipt resolver and owner enrollment resolver. `createSopAuthorityHost` requires `policyId`; `resolveOwner` must return the authenticated owner subject, canonical owner role and project. Never construct these callbacks from request JSON or allow a caller to label its own identity. `createFixtureSopAuthorityHost` forces fixture assurance. Operator control-directory ACL protection is a deployment precondition; hashes and private process objects do not protect against arbitrary code running as the store owner. The internal lifecycle/store composition seam is not part of the public SOP API.

Public `saveVersion` retains canonical content only; public `append` accepts unverified declarations only. Neither creates approval history. Writer handles are private, bound to a particular store, SOP and exact lock-file identity/token. Raw handles, cross-SOP/cross-store handles and caller-selected lock paths are rejected. History and content are immutable bounded ordinary files; one atomic event supersedes the exact old Effective version with an Approved version. Real process-death recovery is still held; do not delete uncertain locks automatically.

Conformance requires a verified Effective snapshot and a trusted runtime resolver returning `{ run, bindings, receipts }`. The retained `run` must bind project, SOP/version, semantic hash, actual compiled-map hash, run ID, required environment, input digest and valid start time. Each binding identifies one obligation's actual producer subject/dispatch, source runtime and exact artifact ID/kind/path/hash. Receipts require explicit enum status, unique receipt ID and SHA-256 payload digest (`digest` of all fields except `receiptHash`), trusted origin, exact run/step/obligation/producer/artifact identity and fresh nonfuture observation time. Each acceptance check includes `{ definition, passed, artifactHash }` matching a canonical required check and the actual artifact. All required global/step obligations, outputs and checks must be covered; empty requirements do not prove a completed step. Raw receipt arrays or aggregate `passed` flags are insufficient. The resolver is trusted host injection and must authenticate retained runtime association; it must never echo user-supplied receipts. Missing production enrollment/association remains an integration hold.

Fixture hosts or permitted fixture-origin evidence yield at most `fixture-conformance`, even when content relaxes origin policy. Missing, stale or inconsistent evidence remains not-observed/nonconformant. Skip and exception decision execution adapters are unavailable, so caller flags cannot prove those routes. Compilation and conformance do not execute SOP steps. Standalone imported snapshots have no private proof and therefore cannot produce conformance.

Standalone CLI contract/import JSON reads are bounded to 1 MiB of actual bytes, projection reads to 8 MiB, before parsing. Ordinary-file/ancestry/identity checks reject aliases and growth; input failures use fixed messages. Human projection encodes HTML and Markdown metacharacters in untrusted text while preserving generated anchors, so links, images, headings and fences remain inert.

## Native independent review integration

A trusted application can compose `createNativeSopReviewHost` with its existing capability broker, owner enrollment, fixed reviewer enrollment, native review transport, evidence verifier and retention callbacks. The transport must observe an actual separately dispatched reviewer and bind its returned dispatch metadata to the pending nonce and exact review bundle. It must not construct reviewer authority from model output, a pasted transcript or imported JSON. Native collaboration is supplied by the host; this module does not launch a Codex client, call a paid API or add another orchestrator.

`reviewDraft(lifecycle, contract)` reviews only the exact retained Draft. It binds the SOP/version, canonical and semantic hashes, bundle, report bytes, actual dispatch, freshness and retained evidence. Private synchronous actor guards recheck the native lease and the exact evidence at the lifecycle's final commit boundary. Modified reports/contracts, replayed dispatches, stale evidence, revoked authorization and rejected reviews cannot advance the Draft. The application verifier must derive acceptance from the exact reviewer report and its material findings; an envelope boolean is insufficient evidence.

Successful review reaches only `Reviewed`. Approval, activation and runtime conformance retain their existing independent gates. Fixture hosts remain fixtures even when a real native reviewer supplied the report. This integration does not establish a protected production store, model identity or adversarial operating-system confinement. The standalone CLI still requires the trusted application bridge for authoritative transitions.

## Selected SDLC runtime association

The internal selected-SDLC association binds one privately verified Effective snapshot to the existing six-phase governed workflow: `create-story`, `validate-story`, `plan-implementation`, `implement-story`, `run-tests`, then `review-story`. Each step is bound to its actual task ID, resolved task-contract hash, project root, input and output paths, checks, approved operation hashes, environment, lifecycle head, and run inputs. Preparation is distinct from structural compilation; compiled SOP maps remain `executable: false`.

The trusted embedder constructs the association and passes its private controller to `runGovernedWorkflow`. Composition explicitly binds the logical lifecycle project ID to the actual project root, framework root, runner project identity, control store, host instance and policy revision; the logical ID is not derived from the filesystem path. Request JSON, imported dispatch IDs, transcripts, unbranded execution bindings, and unbranded hook-shaped objects cannot create this authority.

Association records require a live private issuer tied to that exact controller and store. The public store methods reject copied or caller-computed JSON without the issuer, and the resolver checks the exact run-header, dispatch and outcome hash links. A completed outcome remains provisional after its immutable diagnostic record is retained. The process-private issuer marks it conformance-eligible only after the terminal byte, identity, lifecycle, store, and live execution-binding checks finish without another await. Inspection retains provisional records and identifies their hashes; conformance resolution excludes them. Issuer provenance and eligibility are process-private: restart/import recovery cannot authenticate these records yet and remains unavailable. Hashes and private objects do not claim protection from arbitrary code executing as the same store owner.

The runtime retains a pending dispatch after governance and capability admission and before the provider call, then revalidates Effective authority and every branded binding lease after preparation retention, dispatch retention, and at every governed effect boundary. A revocation after pending retention produces no new provider output. Acceptance captures the checked artifact bytes and filesystem identity before settlement, rejects verifier-window or settlement-window changes, and requires every approved selected-SDLC operation instance to finalize successfully. The binding is revalidated immediately before and after terminal settlement and again after terminal retention. After retention, the runtime rereads the exact artifact bytes, size, and file identity that acceptance checked before it makes the retained completed outcome eligible. Terminal retention and resolver returns revalidate authority after their awaits. Replays, mapping drift, owner drift, unsupported control flow, lifecycle changes, byte or file replacement, lease revocation, and retention failures fail closed. Already observed filesystem effects and immutable provisional diagnostics remain available for investigation but cannot conform.

The association does not add an executor or a public lifecycle host. A fixture lifecycle host still produces only `fixture-conformance`, including when all six deterministic phases perform real filesystem operations. Production transition and ordinary CLI execution remain unavailable until the application supplies the separately authenticated reviewer and lifecycle bridge.

On a supported native candidate-validation host, run the focused real-operation smoke from a source tree with:

```powershell
npx jest tests/unit/workflow-engineering/sop-runtime-association.test.js -t "retains pending dispatches before effects" --runInBand
```

The smoke uses the existing private native candidate authorization, writes only to disposable roots, asserts all six before-dispatch and terminal records, recomputes artifact hashes from disk, and expects `fixture-conformance`. Tests are not included in the npm package, so installed-runtime validation must execute the same harness externally against the unpacked package root; package presence alone is not runtime or production proof.
