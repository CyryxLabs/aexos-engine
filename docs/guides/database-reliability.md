# Read-only database reliability

Story AEX-4.24 provides a closed request and analysis layer plus a bounded PostgreSQL 16 adapter for an operator-controlled disposable fixture. The live adapter uses exactly `pg@8.23.1`, one injected `Client`, one read-only repeatable-read transaction, fixed catalog and plan templates, rollback, and acknowledged disconnect. It does not support customer endpoints, production authentication, arbitrary SQL, mutation, backup execution, file publication, or Supabase/provider certification.

## Commands

The leaf command exposes two operations for root CLI registration:

```text
aexos database validate request.json --json
aexos database audit request.json --json
```

`validate` performs a bounded ordinary file read and returns only request identity. The ordinary root command has no database authority and exits nonzero with `DATABASE_ADAPTER_UNAVAILABLE` before registry, credential, or connection access. A trusted process may compose the leaf command with `createDatabaseCommand({ host })`; there is no CLI flag, environment variable, module path, URL, or request field that can create that authority. SQL, passwords, output paths, mutation flags, and arbitrary executor options are not supported.

The trusted host supplies the reviewed adapter, process-local `CapabilityBroker`, opaque lease, fixed principal/task, and connection registry. The registration is limited to literal loopback, an opaque endpoint/database identity, expected database/login/major, allowed schemas/checks, positive maxima, trusted expected manifests, backup declarations, one sealed migration-relation identifier, an exact migration-object baseline, verified policy-expression hashes, and a controlled plan baseline. The lease binds the complete request hash, resource, scope, effective limits, manifest and baseline hashes, and migration-relation identifier. Registry and secret resolution consume the total deadline. A callback that has begun keeps ownership of the deadline until bounded teardown reaches an acknowledged or explicitly unresolved result; a late callback cannot publish success. Bounded rejection does not prove that an arbitrary hung physical driver connection was destroyed.

At connection time the adapter disables ambient connection discovery by providing every connection field explicitly. It verifies the exact server version and major, database/login, read-only transaction mode, positive effective statement/lock/idle timeouts, and a restricted login with no ownership, membership, CREATE, TEMP, relation or column write privilege, unsupported relation exposure, superuser, BYPASSRLS, role/database creation, or replication authority. It observes every requested namespace and propagates missing namespace coverage as incomplete.

Before either a history `SELECT` or fixed `EXPLAIN`, the applicable baseline inspects the exact attached relation objects. It rejects partial or expression indexes, included columns, invalid/not-ready/dead indexes, non-btree index methods, non-builtin method handlers, unsupported key types or collations, non-builtin opclasses/families, and any family support procedure or operator implementation outside `pg_catalog` internal code. Index, constraint, collation, operator-family and support-object OIDs are included in the observed identity. Planner-consumed constraints are restricted to the exact validated, nondeferrable builtin primary-key shape; check/exclusion/foreign/extra unique constraints and generated/default expressions are outside the supported planning boundary. The fixed plan relations additionally require plain `int4` columns and builtin `int4_ops`. Migration parents require the exact text/int4 layout, `pg_catalog.default` for text, builtin text equality and `octet_length(text)`, and one of the sealed internal relation templates. A matching registered digest cannot override an unsafe current fact. Plans and migration history read `ONLY` their fixed relation, and all raw plan payloads share one aggregate byte budget before projection. Missing, changed or unsafe baseline data leaves the executable check `NOT_ASSESSED` while safe catalog checks continue. Migration history still does not verify the SQL that originally executed a migration.

Both executable baselines require the trusted registration to declare `exclusiveControl: true`. This is an owned-fixture operating assumption covering the interval between catalog observation and the later history planning or `EXPLAIN`; the digest itself is not a lock. PostgreSQL catalog reads and planning are separate dispatches, so concurrent authorized DDL could invalidate the observation. The component therefore supports only the retained fixture under owner-enforced exclusive control and does not claim generic safety against a hostile superuser or an independently mutating database. Registrations without that assumption fail closed to `NOT_ASSESSED`.

## Request boundary

Requests use `aexos.database-audit.request/v1`, PostgreSQL major 16, the exact `database:readonly-audit` capability, one to sixteen explicit schemas, explicit checks, and every finite limit. The closed schema rejects extra fields. It also rejects credential-bearing keys and documented recognizable credential patterns before hashing. This is deliberately bounded pattern detection; it does not claim to identify arbitrary unknown secrets.

The fixture plan DSL is limited to module-owned `aexos_fixture.accounts` and `aexos_fixture.events` relations inside the requested schemas, built-in columns, `int4` equality parameters, fixed projections/order, and a bounded limit. It cannot accept raw SQL, expressions, joins, functions, operators, comments, multiple statements, `ANALYZE`, `COPY`, `WITH`, `CALL`, or `DO`. The low-level compiler is private. Generated statements and nested parameters are deeply immutable; dispatch identity binds the template and typed parameters. Copied objects are denied.

## Fixture evidence

Fixture observations use `aexos.database-audit.fixture-observation/v1`. They are always labeled `sourceKind: fixture` and `adapter.verified: false`. Validated observations are bound to the exact request hash; reuse under a different scope or policy revalidates every limit and binding. `coverage.coveredSchemas` declares the admitted requested scope. Foreign facts are rejected, complete coverage must name every requested schema, and partial catalog coverage propagates to dependent checks. Analysis reports deterministic, hash-linked structural findings for:

- expected structural constraints, with not-null facts separate from actual primary-key, foreign-key, unique, and check constraints;
- valid, ready, full indexes with ordered key and INCLUDE columns; partial, expression, invalid, not-ready, and wrong-order indexes do not satisfy a full-index expectation;
- expected migration order and hashes;
- RLS enablement, policy presence, and a trusted seeded always-true classification;
- PUBLIC grants, elevated role flags, and incomplete role graphs;
- incomplete backup schedule, retention, encryption, and receipt metadata;
- declared fixture plan estimates.

Object identifiers are converted to typed hashes before they enter findings. Raw plan text, policy bodies, rows, errors, comments, connection material, and recognizable credential data are excluded. Estimated plans require a valid tree. Duplicate table, constraint, index, migration, RLS table/policy, role, grant, and plan identities are rejected before analysis. Empty, partial, denied, and unavailable evidence produce `NOT_ASSESSED` or `TRUNCATED`; they do not produce an all-clear result.

`maxRowsPerCheck` counts every admitted fact for that check, including nested constraints, expected constraints, indexes, expected indexes, policy roles/grants, policies, and plan nodes. `maxRowsTotal` counts all admitted fixture facts once across the observation. Plan depth and nodes are bounded after safe projection; `maxPlanBytes` applies once to the aggregate raw payload from all returned plans. The metadata-byte and string limits remain separate ceilings. An RLS request automatically collects the bounded relation ACL facts required by RLS grant rules even when no privilege report was requested.

Even a clean fixture control retains limitations for policy semantics, tenant isolation, restore readiness, fixture declaration authenticity, server read-only enforcement, and provider behavior. A report digest proves deterministic local processing only.

## Live evidence and limits

A successful composed run uses `aexos.database-audit.live-report/v1`, `sourceKind: database_observation`, `environment: disposable-fixture`, and separate live receipt data. Backup fields and coverage remain `operator-declaration`; migration findings identify combined database observation and operator-manifest provenance and retain `MIGRATION_SQL_NOT_VERIFIED`. The report records exact server version, effective registered policy, and a stable normalized metadata hash. Backend PID and observation time exist only in the live receipt, so repeated unchanged audits have equal collected-metadata and canonical-content identities while session receipts may vary. The receipt binds the request, registered connection identity, dispatch hashes, effective limits, cleanup, observation time, metadata hash, and its own digest. The composed CLI prints the complete result so this receipt is retained. Fixture JSON remains permanently unverified and cannot be promoted to live provenance.

The retained PostgreSQL 16 fixture harness snapshots schemas/classes, attributes/defaults, constraints, indexes, inheritance, policies, roles/memberships, database/schema/table/column ACLs, sequence definitions, and every synthetic table row digest before and after product audits. Current fixtures contain no sequences, so current sequence values were not tested. It preserves the inherited migration child and the R3 custom partial-index predicate. The unsafe parent is refused before history dispatch with zero predicate-function notices even when the registration contains a newly matching digest; an isolated ordinary builtin parent supplies the positive migration and `ONLY` controls. The harness also verifies genuine clean/seeded pairs, missing-schema coverage, RLS-only grant dependencies, aggregate raw-plan bounds, stable repeated content identity, server write refusal, effective row/metadata limits, baseline refusal, statement/lock/total timeout rejection, statement capture, and absence of remaining real audit sessions. The five-check clean control covers schema, indexes, migration, plans, and backup declaration; a separate clean RLS-only control exercises its ACL dependency. Neither is an all-seven-check clean claim, and privilege graph coverage remains partial. Invalid/not-ready index states are covered by deterministic projection controls because safely manufacturing those internal catalog states was not authorized. Backup completeness remains an operator declaration and is not restore verification. These results establish only local disposable-fixture behavior. RLS tenant isolation, restore readiness, customer authentication, hostile-server memory isolation, provider behavior, and installed/root authority remain separate acceptance boundaries.

## Reusable composition harness

`tests/integration/database-reliability/postgres-live.test.js` is the retained live harness. Set `AEXOS_RUNTIME_ROOT` to the installed candidate root and, when that root does not contain test fixtures, set `AEXOS_DATABASE_REQUEST_FIXTURE` to the reviewed request JSON. The harness resolves `pg`, the database API, broker, durable-evidence helpers, and leaf CLI from that runtime root. `AEXOS_POSTGRES_FIXTURE_CONFIG` remains owner-harness input only; never print, copy, or hash it. `AEXOS_DATABASE_EVIDENCE_DIR` selects a fresh retained evidence directory.

The composition API is `createPostgresAdapter({ Client, driverVersion: '8.23.1' })`, `createPostgresScope(identity, registration)`, and `auditDatabase(identity, host)` from `.aexos-core/core/database-reliability`, plus `createDatabaseCommand({ host })` from `.aexos-core/cli/commands/database`. The host must contain the adapter, broker, opaque lease token, fixed principal, and connection registry. The stable request fixture is `tests/fixtures/database-reliability/request.json`; clean and seeded controls are constructed only inside the owner harness from trusted registrations and retained local fixture objects.
